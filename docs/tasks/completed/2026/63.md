# Issue 63 handoff

## Objective

Build `Vst3TimelineFileStoreV1` in the vst-host lane: a bounded, fail-closed
per-timeline file store on top of the merged Issue #35 canonical persistence — one
`<id>.json` document per timeline in a caller-chosen directory, atomic replace,
strict filename-safe ID subset ([A-Za-z0-9._-], <=64 bytes) with a bijective
ID-to-filename mapping, fixed capacity and deterministic enumeration. No new schema;
the accepted `vst3-parameter-timeline-v1.schema.json` format is reused as-is.

## Acceptance

- Save/load round-trips validator-passing snapshots through real files.
- Strict ID sanitization rejects empty, traversal, separator, oversized and
  non-ASCII IDs before any filesystem access.
- Load of a missing file returns not_found; corrupt/wrong-schema content returns
  parse_error and leaves the destination untouched (inherited from Issue #35).
- Remove deletes exactly the mapped file; double-remove reports not_found.
- Fixed capacity enforced at open time; enumeration is bounded and deterministic.
- No IPC frame, schema file, RT-thread, driver or permanent-identity change.

## Known limitations

- The store keeps IDs to the strict filename-safe subset; scheduler timeline IDs
  outside that subset cannot be stored until a mapping layer exists.
- Enumeration reflects the directory contents at scan time; concurrent external
  writers are out of scope for this single-writer control-plane contract.
- User-space source-contract work only; proves nothing about physical audio,
  per-App delivery, drivers, HLK or signing.
